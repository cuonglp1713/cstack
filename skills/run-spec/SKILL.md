# Implement one bounded change

1. Read repo instructions, `.cstack/CONTEXT.md`, the active `.cstack/PLAN.md` and `.cstack/PROGRESS.md` if the private kit is present, and relevant source, tests, contracts, and feature-map detail. Use the specs-root `README.md` to locate the active spec and authorized slice, then read its scope, plan, and steps under the project's existing filenames. `README.md`, phase plans, and child/task tables can fulfill those roles; do not require a separate `tasks.md`. Open a completed spec only when the task depends on it. Compare notes with Git status and current code; copied templates or missing records do not establish application state.
2. State the observable outcome, in/out scope, acceptance criteria, and likely files. A direct user request for a defined feature or fix authorizes implementation, including when the kit has just been adopted and no spec exists yet. For substantial tracked work, create the spec record described in `.cstack/CONTEXT.md` once the scope is clear; a focused fix can proceed directly when no durable record is needed. Do not gate work on inventorying unrelated features or reconstructing old specs. Surface any new product decision, incompatible contract change, or external rollout while completing independent authorized work.
3. Follow the project's actual architecture and directory layout. For a FastAPI project without an established structure, prefer thin routers, typed schemas, domain services, DB/models, and separate worker entry points when needed. Repo-specific choices override global stack defaults.
4. Implement the smallest coherent change within the authorized slice. A spec can span multiple phases/slices, with one implementation slice active at a time. Update steps in the existing child/task table or `tasks.md`, and keep the specs-root index current. Preserve unrelated edits. Add tests only when they prove behavior or protect a meaningful invariant. Use disposable infrastructure for migration/integration checks.
5. Verify the user-visible result and relevant side effect using `verify-backend` where applicable. Inspect the diff and record failures and skipped checks accurately.
6. Use `handoff-spec` after material work to record implementation and observed results in the existing result report (`result.md` or `PHASE-*-RESULTS.md`), and update the living indexes. Preserve the project's filenames and avoid duplicate reports. Record team-relevant behavior and decisions in shared project artifacts when required. Close the requested slice from evidence; close the spec only when its overall acceptance is met. Continue slices already covered by the user's request; do not infer authorization for unrequested work from a green test, merge, or completed slice.
