# Leave the next session a reliable starting point

1. Check current branch, Git status/HEAD, changed source, relevant tests, and `.cstack/PLAN.md`, `.cstack/PROGRESS.md`, and `.cstack/VERIFY.md` when the private kit is present. Use the specs-root `README.md` to locate the current spec and slice when present; otherwise use the repo's handoff documents. Distinguish committed behavior from uncommitted work and ignored files. In an adopted repo, empty kit templates do not describe product history.
2. For tracked substantial work, update the existing result report (`result.md` or `PHASE-*-RESULTS.md`) with implemented behavior, changed code/commit, exact verification command and environment, observed result and side effect, limits, decisions, and remaining work. Preserve the project's naming convention; update its child/task table or `tasks.md` without duplicating steps. A spec may contain several phase reports. Do not create a retrospective spec for old features. For a focused fix without a spec, keep concise private results in the living files or follow the repo's established handoff convention.
3. Create or update the short specs-root `README.md` for actual tracked work, using the project's location (`.cstack/specs/` by default, or existing `specs/`). Keep current work, status, active or waiting slice, next action, and links to the relevant plan/results there. Point other living files to it instead of copying history. In `.cstack/PROGRESS.md` when present, keep a concise handoff and completed-spec links; do not imply full coverage of an adopted repo. Keep detailed decisions and evidence in linked reports, and each spec's README focused on scope and phase links.
4. In `.cstack/PLAN.md` when present, keep a pointer to the current index and plan. In `.cstack/VERIFY.md`, keep reusable commands and a concise pointer to the latest proof report. Before replacing pointers, preserve unique decisions and results. Mark a slice done from its acceptance evidence; mark the spec done only when its overall acceptance has observed evidence or the user explicitly accepts a documented limitation. Otherwise retain its actual state. Continue already authorized slices; a completed slice, test pass, or merge does not authorize unrequested work. Do not paste long logs or secrets.
5. Update affected `.cstack/FEATURE_MAP.md` rows when user journeys or proof paths change. Keep it a short repo-specific index, leave uninspected journeys unmapped, and link longer personal detail in `.cstack/docs/features/` when needed. Put lasting personal decisions in `.cstack/docs/adr/`. Record team-relevant decisions and instructions in shared project artifacts when required.
6. Before shortening or archiving a document, preserve every unique result, decision, and limitation in the spec report or an ADR and leave a pointer. After moving files, verify outgoing relative links and incoming links from indexes or other documents, including evidence artifacts. Completed spec records are historical; later changes get a new spec linked to the earlier record. End with a self-contained summary of changed behavior, proof, remaining uncertainty, and next action.
