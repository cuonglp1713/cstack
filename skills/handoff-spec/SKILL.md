# Leave the next session a reliable starting point

1. Check current branch, Git status/HEAD, changed source, relevant tests, and `.cstack/PLAN.md`, `.cstack/PROGRESS.md`, and `.cstack/VERIFY.md` when the private kit is present. Locate the current spec and slice through PROGRESS and read the intended scope in PLAN; otherwise use the repo's handoff documents. Distinguish committed behavior from uncommitted work and ignored files. In an adopted repo, empty kit templates do not describe product history.
2. For tracked substantial work, update the existing result report (`result.md` or `PHASE-*-RESULTS.md`) with implemented behavior, changed code/commit, exact verification command and environment, observed result and side effect, limits, decisions, and remaining work. Preserve the project's naming convention; update its child/task table or `tasks.md` without duplicating steps. A spec may contain several phase reports. Do not create a retrospective spec for old features. For a focused fix without a spec, keep concise private results in the living files or follow the repo's established handoff convention.
3. In `.cstack/PROGRESS.md` when present, record the active or waiting spec/phase/slice, execution status, last completed work, blocker, next action, and plan/results links. Keep completed-spec links in a short index here; do not imply full coverage of an adopted repo or append a full event log. Keep detailed decisions and evidence in spec/phase records. Do not create an additional specs-root progress README.
4. Keep `.cstack/PLAN.md` focused on intended outcome, scope, acceptance, approach, dependencies, risks, verification plan, and detail links; update it when that plan changes, not for every execution-status change. In `.cstack/VERIFY.md`, keep reusable commands and the latest observed proof summary with environment, limits, and report links. Before replacing pointers, preserve unique decisions and results. Mark a slice done from its acceptance evidence; mark the spec done only when its overall acceptance has observed evidence or the user explicitly accepts a documented limitation. Otherwise retain its actual state. Continue already authorized slices; a completed slice, test pass, or merge does not authorize unrequested work. Do not paste long logs or secrets.
5. Update affected `.cstack/FEATURE_MAP.md` rows when product journeys, delivery state, entry points, owning code, or proof links change; keep phase/task status in PROGRESS. Leave uninspected journeys unmapped and link longer personal detail in `.cstack/docs/features/` when needed. Update CONTEXT for changed stable project decisions and link longer personal rationale in `.cstack/docs/adr/`. Record team-relevant decisions and instructions in shared project artifacts when required.
6. Before shortening or archiving a document, preserve every unique result, decision, and limitation in the spec report or an ADR and leave a pointer. After moving files, verify outgoing relative links and incoming links from indexes or other documents, including evidence artifacts. Completed spec records are historical; later changes get a new spec linked to the earlier record. End with a self-contained summary of changed behavior, proof, remaining uncertainty, and next action.
